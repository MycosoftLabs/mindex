# MINDEX to MAS Research Identity Export Compatibility

## Scope and source pins

This is a static, source-grounded compatibility review at MINDEX commit `a60f2f309c438f375313f8c843877dc9881aaf7b` on isolated branch `codex/research-identity-export-oct04`. It does not modify PR #34 or call a database, provider, Website, first40/16, FG026, wallet, or live service. No exporter or consumer code was changed.

The pinned MAS consumer is `research_jobs/identity_snapshot.py` from the offline installed-package receipt for MAS PR #202 head `b886147511021672f1e1ac488ee5d883a75516be`; its SHA-256 is `a95d735d58051a13101e1537a42f88eb1d7381beb193e40346464adcac9b6979`. Its `research.identity-export.v1` validator requires each record to contain exactly `resource`, `accession`, `sequence_sha256`, `canonical_taxon_id`, `canonical_reference_id`, and `source_record_id`; all three identity fields must be canonical UUID strings. It also requires an authority URL, authority-response SHA-256, capture time, expiry, and one of `available|empty|partial|unavailable`. Duplicate `(resource, accession, sequence_sha256)` keys reject the entire export.

## MINDEX identities that actually exist

| Identity | Committed MINDEX representation | Semantics and limitation |
|---|---|---|
| Canonical taxon | `core.taxon.id UUID`; `core.taxon_external_id.id UUID`, with `source` and `external_id` both text | A canonical taxon UUID exists when the row is linked. External NCBI taxids remain provider strings and are not canonical UUIDs. |
| Genetic sequence | `bio.genetic_sequence.id SERIAL`, `accession VARCHAR(50)`, `version VARCHAR(20)`, `taxon_id UUID`, `sequence TEXT`, source fields, and JSONB metadata | The GET route selects stored accession/version/sequence/taxon/provenance. The table has no UUID source-record key, no dedicated sequence-hash column, and no authority snapshot/expiry columns. Hashing stored sequence bytes can produce a sequence digest but cannot recover the original EFetch response. |
| Local publication/reference row | `core.publications.id VARCHAR(64)`, `source`, `external_id`, and publication fields | This is an opaque local string primary key, not a UUID canonical-reference identity. For the new GenBank evidence path, the ID is the first 32 hex characters of SHA-256 over provider and external ID; it is not UUID-formatted and must not be cast or reformatted as one. |
| Source-attested publication evidence | `bio.publication_taxon_evidence.evidence_id UUID`; `publication_id VARCHAR(64)`; `taxon_id UUID`; `provider_taxon_id TEXT`; `provider_source_record_id TEXT`; source and normalization hashes | `evidence_id` is a MINDEX evidence-row key generated by `gen_random_uuid()`. It is not the provider's source-record ID. Provider source identity is text such as `PZ955173.1#reference=1`. The raw EFetch XML bytes are hashed while parsing and the hash is retained, but the raw XML itself is not persisted by this importer. |

The GenBank evidence writer parses an exact versioned accession and each cited reference, then inserts a publication row and evidence row. It retains exact provider taxon text, provider source-record text, source-content SHA-256, normalized-payload SHA-256, and review state. It does not create a canonical reference UUID or a UUID for the provider record. The ordinary genetic-sequence importer stores sequence data separately; this evidence writer does not attach a sequence hash to the publication row.

The migration inventory and source search found no MINDEX `canonical_reference_id`, UUID source-record column, persisted raw GenBank response table, or native `research.identity-export.v1` exporter. `bio.publication_taxon` is a reviewed publication/taxon relation keyed by `publication_id VARCHAR(64)` and `taxon_id UUID`; it does not add either missing identity. The older `core.publication_taxa` migration is not a substitute and does not establish canonical-reference UUIDs.

## Exact read-only schema and candidate-row queries

These statements are inspection/proposal text only; none was run against any database.

Schema/type inventory for the identities in scope:

```sql
SELECT table_schema, table_name, column_name, data_type, udt_name, is_nullable
FROM information_schema.columns
WHERE (table_schema, table_name) IN (
    ('core', 'taxon'),
    ('core', 'taxon_external_id'),
    ('core', 'publications'),
    ('bio', 'genetic_sequence'),
    ('bio', 'publication_taxon'),
    ('bio', 'publication_taxon_evidence')
)
ORDER BY table_schema, table_name, ordinal_position;
```

Read-only view of the nearest existing sequence/reference/evidence relationship for one exact accession version:

```sql
SELECT
    gs.accession,
    gs.version,
    gs.taxon_id AS canonical_taxon_id,
    encode(digest(convert_to(gs.sequence, 'UTF8'), 'sha256'), 'hex') AS stored_sequence_sha256,
    gs.source,
    gs.source_url,
    e.evidence_id AS mindex_evidence_row_id,
    e.publication_id AS mindex_publication_id,
    p.source AS publication_source,
    p.external_id AS publication_external_id,
    e.provider,
    e.provider_taxon_id,
    e.provider_source_record_id,
    e.source_content_sha256,
    e.normalization_sha256,
    e.evidence_state
FROM bio.genetic_sequence AS gs
LEFT JOIN bio.publication_taxon_evidence AS e
  ON e.taxon_id = gs.taxon_id
 AND gs.version IS NOT NULL
 AND e.provider_source_record_id LIKE gs.version || '#reference=%'
LEFT JOIN core.publications AS p ON p.id = e.publication_id
WHERE gs.version = :exact_accession_version;
```

The sequence digest above is a computed digest of MINDEX's stored UTF-8 sequence text, not a persisted source-response hash. The evidence hash is the exact decoded GenBank EFetch XML hash from the parser. The left join can return multiple citation rows for one accession.version; collapsing them into one identity row would require an explicit reference-selection rule. A source-record row with no exact version/evidence join is absent; multiple candidate references are ambiguous; an accession with a different stored version is a version conflict. These states must not be changed into successful identity matches by choosing a row, using a display name, or substituting a provider taxid.

## Compatibility decision

A conforming v1 export is not feasible from the committed MINDEX schema without fabricating or mislabeling identities. The genuine UUID `core.taxon.id` can populate `canonical_taxon_id` for an exactly linked row. No `canonical_reference_id UUID` exists. The existing source-record ID is provider text, while `evidence_id UUID` identifies MINDEX's evidence row and is not the source record. `core.publications.id` is text, and the MAS envelope's authority URL/response hash/capture-expiry contract is not represented by a MINDEX snapshot record. Renaming, UUID-casting, or deterministically formatting any of these values would change their semantics.

Recommended narrow consumer-contract change for a MINDEX-native export: keep `canonical_taxon_id` as UUID, but represent local references and provider records as tagged opaque identities, for example `canonical_reference: {namespace: "mindex.core.publications.id.v1", value: "<stored id>"}` and `source_record: {provider: "ncbi_genbank", id: "<provider_source_record_id>"}`. Keep `evidence_id` separately named as a MINDEX evidence-row UUID. Give the database snapshot its own envelope (`producer`, snapshot ID, capture time, export digest, and status) instead of claiming an authority-response URL/hash. This requires MAS consumer adaptation; this MINDEX branch does not implement it.

If the consumer retains mandatory UUID canonical-reference and source-record fields, MINDEX needs a separately reviewed schema/identity design that creates and persists those identities with provenance. A UUID default on an evidence row does not itself satisfy either identity. No migration, backfill, source enrichment, or apply is proposed here.

For a future producer after contract resolution, preserve status distinctions: `unavailable` for absent required relations/columns or query failure; `empty` only when all required reads succeed and the bounded request yields no candidate; `partial` when rows exist but some lack a unique exact taxon/reference/source/version/hash binding; and `available` only when every exported row has the required verified identities and hashes. Report absent, ambiguous, version, and hash conflicts explicitly; never make a conflicting row look like an empty successful result. The current strict v1 consumer only accepts valid UUID rows and does not accept per-row conflict diagnostics, another reason not to emit a fabricated v1 envelope.
